LLM Serving Frameworks — 5~7장이 "무엇을 어떻게 최적화하는가"였다면, 이 장은 "그 최적화들이 실제로 어느 코드에 어떻게 얹혀 있는가"입니다.

프레임워크가 넷입니다 — vLLM, TensorRT-LLM, SGLang, llama.cpp. 그중 vLLM은 안을 열어 봅니다. 스케줄러가 토큰을 어떻게 나눠주는지까지요.

이 자료가 지키는 것

① 서빙 프레임워크는 래퍼가 아닙니다. 스케줄러 · KV 캐시 매니저 · 모델 익스큐터 · 워커 · 분산 실행 · 최적화 계층을 가진 런타임입니다.
② 앞 장의 기법이 어디에 들어가는지 짚습니다. 연속 배칭도 청크 프리필도 프리픽스 캐싱도 전부 스케줄러 한 곳에서 만납니다.
③ 그림 15개 전부 조작 가능. 큐와 토큰 예산은 직접 밀어봐야 감이 옵니다.
④ 원문 도식은 다시 그려서 실었습니다. 캡처가 아니라 이 페이지의 색과 글꼴로요.

들어가며

읽는 시간 약 45분 대상 vLLM 안을 열어보고 싶은 사람 사전 지식 CH6 배칭·KV 캐시 · CH7 병렬화 그림 15개 조작 가능 + 원문 도식 12개 재현

여기까지 온 길을 되짚어 봅시다. 5장에서 어디가 병목인지 배웠고, 6장에서 한 GPU 안에서 그 병목을 옮기는 법을, 7장에서 GPU 여러 장으로 넘어가는 법을 배웠습니다.

그런데 그 기법들은 여러분이 직접 구현하는 게 아닙니다. 어딘가에 이미 들어 있습니다. --enable-chunked-prefill 한 줄로 켜지는 그것이 실제로 어느 객체의 어느 메서드에서 일어나는지, 이 장에서 열어봅니다.

결론부터 네 줄
  1. 범용 서빙 프레임워크는 LLM에 안 맞습니다. TF Serving·TorchServe·Triton은 입력이 짧고 고정된 워크로드용으로 설계됐습니다.
  2. vLLM의 중심은 스케줄러입니다. 배칭·캐싱·청크 프리필이 전부 여기 모입니다 — 그리고 모델이 뭔지 모른 채로 합니다.
  3. 최적화는 자기 계층에서 합니다. 스케줄러 → ModelExecutor → 모델 레이어 → CustomOp. 그래서 새 GPU가 나와도 맨 아래만 바꿉니다.
  4. "어느 게 최고인가"가 아니라 "내 상황에 뭐가 맞나"입니다. 그리고 그 답은 3~6개월마다 다시 물어야 합니다.

01왜 전용 프레임워크인가 — 다섯 가지가 다릅니다

한 줄 요약: 기존 서빙 프레임워크는 "입력이 짧고 모양이 고정된" 워크로드용으로 설계됐습니다.

왜 이걸 배우나
"TorchServe도 모델 서빙인데, LLM만 왜 따로 있지?"

LLM 시대 전에도 서빙 프레임워크는 많았습니다 — TensorFlow Serving, TorchServe, NVIDIA Triton. 그런데 그것들은 이미지 인식이나 정형 데이터 추론을 위해 설계된 것이었습니다.

원문의 진단이 정확합니다 — 그런 워크로드는 "입력 크기가 짧고, 텐서 형태가 고정되어 있으며, 지연 시간 요구사항을 예측할 수 있어서, 주된 최적화 대상은 대체로 배치 처리였습니다."
LLM은 그 네 가지가 전부 다릅니다.

LLM 서빙의 고유 과제 다섯 가지 — 원문 그대로

① 자기회귀적 생성 — LLM은 한 번에 하나의 토큰씩 출력을 만듭니다. 이미지 모델과 달리 추론 세션이 수 초에서 수 분 동안 열려 있을 수 있습니다.
② 컨텍스트 길이의 폭증 — 몇 개의 토큰부터 수십만, 심지어 백만 개에 이르는 프롬프트까지 처리해야 합니다. KV 캐시 메모리 관리가 중대한 병목이 됩니다.
③ 연속 배칭 — 요청마다 입력과 출력 길이가 크게 다릅니다. 정적 배칭 전략은 GPU를 제대로 활용하지 못합니다.
④ 스트리밍 요구사항 — 사용자는 TTFT가 수백 밀리초 이내이길 기대하고, 지속적인 토큰 스트리밍도 요구합니다.
⑤ 자원 활용 — GPU는 비쌉니다. 파편화나 유휴 토큰으로 인한 GPU FLOPS 낭비는 대규모 환경에서 용납될 수 없습니다.

다섯 개를 하나씩 뜯어보면 익숙한 이름들이 나옵니다. ②는 6장의 PagedAttention이 푼 문제이고, ③은 6장의 연속 배칭, ⑤는 6장의 파편화 이야기입니다. 즉 앞 두 장에서 배운 기법들이 통째로 "범용 프레임워크가 못 하는 것" 목록인 셈입니다.

그래서 나온 것

원문의 정리 그대로 — "이러한 요구를 충족시키기 위해 vLLM, TensorRT-LLM, SGLang과 같은 새로운 부류의 프레임워크 '전문 LLM 서빙 프레임워크'가 등장했습니다."

이들이 들고 온 것은 페이지 단위 KV 캐싱, 연속 배칭, LLM 전용 양자화, 추측 디코딩 — 전부 6장과 7장에서 본 것들입니다.

한 문장으로 — 프레임워크는 래퍼가 아닙니다

원문의 핵심 요약입니다. "LLM serving framework가 단순 inference wrapper가 아니라 scheduler, KV cache manager, model executor, worker, distributed execution, optimization layer를 포함하는 runtime이라는 점."
이 목록이 이 장의 목차이기도 합니다.

1장 세 줄 요약
  1. 범용 서빙은 입력이 짧고 모양이 고정된 워크로드용이었습니다. LLM은 그 전제가 전부 깨집니다.
  2. 고유 과제는 자기회귀 · 컨텍스트 폭증 · 연속 배칭 · 스트리밍 · 자원 활용 다섯입니다.
  3. 이 다섯을 풀려고 PagedAttention · 연속 배칭 · LLM 전용 양자화 · 추측 디코딩을 내장한 프레임워크가 나왔습니다.

02두 개의 티어 — 엔진과 오케스트레이션

한 줄 요약: 오케스트레이션은 토큰을 만들지 않습니다. 엔진 없이는 토큰도 없습니다.

왜 이걸 배우나
"Dynamo도 서빙이고 vLLM도 서빙인데, 둘은 경쟁 관계인가?"

아닙니다. 층이 다릅니다. 7장 마지막에 본 4계층 스택을 다시 떠올리세요 — 라우팅/오케스트레이션이 위에 있고 실행 엔진이 아래에 있었습니다.

이 장의 주인공인 vLLM · TensorRT-LLM · SGLang · llama.cpp는 전부 엔진 티어입니다. Dynamo와 llm-d는 오케스트레이션 티어입니다. 이 구분을 잡고 가야 헷갈리지 않습니다.

이 장에 나오는 낯선 말
Engine tier (엔진 티어)
실제로 토큰을 만드는 계층. 스케줄러 · KV 캐시 · 커널 세 부분으로 나눠 볼 수 있습니다.
Orchestration tier (오케스트레이션 티어)
여러 노드에 걸친 분산 서빙을 조율하는 계층. 스케줄러이자 라우터이지, 엔진이 아닙니다.
The Fleet
오케스트레이션이 관리하는 노드 무리. prefill 풀과 decode 풀로 나뉠 수 있습니다(7장 12장).
원문 도식 재현

엔진 티어 — 같은 3단 구조로 나란히

이 그림이 말하는 것

네 엔진을 같은 3단 구조(스케줄러 / KV 캐시 / 커널)로 놓고 보면 차이가 보입니다.
vLLM — PyTorch 재단 소속이고, 지원 하드웨어가 가장 넓습니다: INTEL, NVIDIA, AMD, TPU, AWS.
SGLang — 96 GPUs · DeepSeek Reproduction. 대규모 클러스터 재현 사례가 강조됩니다.
TensorRT-LLM — NVIDIA 전용. 대신 그 위에서 최고 성능.
TGI — Hugging Face. The Hub 생태계와 통합돼 있습니다.

원문 도식 재현

오케스트레이션 티어 — 그리고 "NO ENGINE, NO TOKEN"

이 그림이 말하는 것

엔진 티어 위에 NVIDIA Dynamo와 llm-d(쿠버네티스 네이티브)가 있습니다. 이들이 하는 일은 여러 노드에 걸친 분산 서빙을 조율하는 것입니다.
노드 1·2는 PREFILL POOL, 노드 3·4는 DECODE POOL입니다 — 7장 12장의 P/D 분리가 그대로입니다.

그런데 아래쪽에 경고가 붙습니다 — "NO ENGINE, NO TOKEN".
오케스트레이션 계층 자체는 추론 엔진을 실행하지도, 토큰을 직접 생성하지도 않습니다. 요청을 스케줄링하고 라우팅만 합니다. 실제 토큰 생성은 각 노드의 엔진 티어가 합니다.

2장 세 줄 요약
  1. 엔진 티어는 vLLM·SGLang·TensorRT-LLM·TGI이고, 전부 스케줄러 / KV 캐시 / 커널 3단으로 볼 수 있습니다.
  2. 오케스트레이션 티어는 Dynamo·llm-d이고, 여러 노드를 조율합니다 — P/D 분리도 여기서 배치합니다.
  3. "NO ENGINE, NO TOKEN" — 오케스트레이션은 라우팅만 합니다. 토큰은 반드시 엔진이 만듭니다.

03vLLM의 두 얼굴 — 라이브러리와 서버

한 줄 요약: 같은 엔진인데 진입점이 둘입니다. 그리고 고르는 기준은 "서버가 필요한가"입니다.

왜 이걸 배우나
"코랩에서는 LLM() 을 쓰고 배포할 땐 vllm serve 를 쓰던데, 둘이 다른 건가?"

안쪽은 같습니다. 둘 다 같은 LLMEngine을 씁니다. 다른 건 바깥 껍데기뿐입니다.

그런데 그 껍데기 차이가 오버헤드와 통합 방식을 바꾸므로, 언제 무엇을 쓸지는 알아둘 값이 있습니다.

두 가지 사용 방식 — 원문 그대로
LLM 클래스API 서버
무엇인프로세스 파이썬 라이브러리, 서버 불필요vllm serve로 실행하는 OpenAI 호환 HTTP 엔드포인트
어디에오프라인 / 배치 워크플로우프로덕션 / 멀티클라이언트 / 스트리밍
주는 것세밀한 제어, 낮은 오버헤드, 자체 서빙 스택과의 손쉬운 통합바로 사용 가능한 네트워크 엔드포인트

원문의 표현으로 "라이브러리 모드"는 vLLM을 기존 서비스나 배치 워크플로우에 직접 연결하고 싶을 때 이상적입니다.

LLM 클래스 — 인프로세스
llm = LLM(
  model="Qwen/Qwen3-7B-Instruct",
  trust_remote_code=True,   # Qwen uses custom modeling code
  dtype="float16",          # Use float16 for GPU
  max_model_len=32768,
  gpu_memory_utilization=0.8,
)

outputs = llm.generate(prompts, sampling)
API 서버 — OpenAI 호환
vllm serve Qwen/Qwen3-7B-Instruct \
  --trust-remote-code \
  --dtype bfloat16 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.8

curl http://localhost:8000/v1/chat/completions \
 -H "Content-Type: application/json" \
 -d '{
   "model": "Qwen/Qwen3-7B-Instruct",
   "temperature": 0.7,
   "max_tokens": 256,
   "stream": true
 }'
같은 파라미터가 두 세계에 그대로 있습니다

max_model_len=32768 ↔ --max-model-len 32768, gpu_memory_utilization=0.8 ↔ --gpu-memory-utilization 0.8.
같은 엔진에 같은 설정을 다른 문법으로 넣는 것뿐입니다. 6장 5장에서 본 --max-num-seqs, --max-num-batched-tokens도 여기 들어갑니다.

전제 하나 — vLLM 인스턴스 하나에 모델 하나

원문의 문장입니다. "vLLM은 단일 모델 서비스 구성에 최적화되어 있으며, 각 인스턴스는 시작 시 하나의 모델을 초기화합니다."
모델을 여러 개 서빙하려면 인스턴스를 여러 개 띄우고 그 앞에 라우터를 둡니다 — 7장 11장의 그 라우터입니다.

3장 세 줄 요약
  1. LLM 클래스는 인프로세스 라이브러리 — 오프라인·배치용이고 오버헤드가 낮습니다.
  2. vllm serve는 OpenAI 호환 HTTP 서버 — 프로덕션·멀티클라이언트·스트리밍용입니다.
  3. 안쪽 엔진은 같고 설정 파라미터도 이름만 바뀌어 그대로 대응됩니다.

04내부 계층 — 여섯 개의 상자가 하는 일

한 줄 요약: 스케줄러는 모델을 모르고, 워커는 스케줄을 모릅니다. 그 분리가 vLLM의 설계입니다.

왜 이걸 배우나
"vLLM 소스를 열었는데 클래스가 너무 많다."

여섯 개만 잡으면 됩니다. 그리고 위에서 아래로 내려가는 한 줄입니다 — LLMEngine → EngineCore → Scheduler → ModelExecutor → GPUWorker → GPUModelRunner.

이 줄에서 딱 한 군데에 금이 그어져 있습니다. 스케줄러와 ModelExecutor 사이입니다. 위쪽은 모델이 뭔지 모르고, 아래쪽은 모델만 압니다.

이 장에 나오는 낯선 말
LLMEngine
vLLM 추론 시스템의 상위 수준 인터페이스이자 주 진입점. 요청 생명주기 전체를 관리합니다.
EngineCore
중앙 오케스트레이터. 모델 익스큐터·출력 프로세서·스케줄러를 묶는 내부 루프(inner loop)입니다.
Scheduler
추론 파이프라인의 교통 관제사. 제한된 자원을 경쟁하는 요청들에 배분합니다.
SchedulerOutput
스케줄러가 ModelExecutor에 넘기는 작업 지시서(work order).
ModelExecutor / GPUWorker / GPUModelRunner
각각 여러 워커 프로세스 조율 / 프로세스별 디바이스·모델 생명주기 / 실제 신경망 실행.
model-agnostic (모델 무관)
어떤 모델이든 똑같이 적용되는 성질. 스케줄러의 최적화가 그렇습니다.
원문 그림 8-1

vLLM 시스템 아키텍처

이 그림이 말하는 것

원문의 설명 그대로 — Configuration(설정), Model Execution(모델 실행), Output Processing(출력 처리)이라는 기능과 관련해 LLMEngine, EngineCore, Scheduler 같은 컴포넌트들의 관계를 보여줍니다.
LLMEngine이 바깥 세계와 만나는 공개 API이고, 그 안에서 EngineCore가 내부 루프를 돌립니다.

그림 4

여섯 상자 — 누르면 그 상자의 일이 보입니다

↔ 버튼 + 슬라이더
해볼 것 — ① 버튼으로 컴포넌트를 차례로 눌러보세요. 각자 무엇을 알고 무엇을 모르는지 봅니다. ② Scheduler와 ModelExecutor 사이의 금(모델 무관 ↔ 모델 특화)을 확인하세요. ③ 워커 수를 늘리면 어느 상자가 여러 개가 되는지 봅니다.
관찰 포인트

스케줄러 위쪽은 모델을 모릅니다. 아래쪽은 모델만 압니다. 이 금이 9장의 4계층 최적화로 이어집니다.

SchedulerOutput — 두 세계를 잇는 계약

스케줄러는 자신의 실행 계획을 SchedulerOutput이라는 데이터 구조에 담아 ModelExecutor에게 넘깁니다. 원문은 이걸 "작업 지시서(work order)"라고 부르고, 그 내용을 이렇게 풀어 씁니다.

"여기 처리할 요청 배치가 있다. 각 요청이 받아야 할 토큰 수는 이만큼이고, 여기 입력 데이터와 파라미터가 있으며, 여기 이들에게 할당된 메모리 블록이 있고, 여기 특별히 처리해야 할 요구사항들이 있다."

이 지시서가 표준화된 계약이라 양쪽이 서로를 몰라도 됩니다. 그리고 실행 결과는 다음 반복을 위해 다시 스케줄러로 피드백됩니다.

원문 그림 8-2

ModelExecutor · GPUWorker · GPUModelRunner

이 그림이 말하는 것

왜 세 겹일까요. 원문의 이유가 명확합니다 — "vLLM은 각 모델을 별도의 프로세스 또는 프로세스 그룹에서 호스팅하고 실행하기 때문에, 프로세스 간 통신을 처리하고, 분산 워커 그룹을 조율하며, 다양한 모델 순전파 실행 세부사항을 처리하기 위해 계층화된 아키텍처를 사용합니다."

즉 세 겹은 각각 프로세스 간 통신 · 디바이스 생명주기 · 실제 실행을 맡습니다. 한 겹이 세 가지를 다 하면 7장의 TP·PP·EP 조합마다 코드를 새로 짜야 했을 겁니다.

핵심 설계 원칙 — 관심사 분리

· 시스템 레벨 최적화(Scheduler)와 모델별 최적화(ModelExecutor/GPUWorker)를 명확히 구분합니다.
· 스케줄러는 토큰 단위 스케줄링, 동적 배칭, 프리픽스 캐싱, 청크 단위 프리필 같은 모델에 무관한(model-agnostic) 최적화를 담당합니다.
· 원문의 문장 — "이러한 관심사의 분리를 통해 각 컴포넌트는 컴포넌트 간의 깔끔한 인터페이스를 유지하면서 자신의 특정 모델 실행 책임에 집중할 수 있습니다."

실용적 결론이 하나 나옵니다 — vLLM은 배칭·스케줄링 최적화를 GPU 실행 로직과 독립적으로 개선할 수 있습니다. 새 스케줄링 아이디어가 나와도 커널을 안 건드립니다.

4장 세 줄 요약
  1. 줄기는 하나입니다 — LLMEngine → EngineCore → Scheduler → ModelExecutor → GPUWorker → GPUModelRunner.
  2. 스케줄러 위는 모델 무관, 아래는 모델 특화입니다. 그 사이를 SchedulerOutput이 잇습니다.
  3. 아래 세 겹이 나뉜 이유는 프로세스 간 통신 · 디바이스 생명주기 · 실제 실행을 따로 두기 위해서입니다.

05모델 초기화 — 네 단계로 워커가 서기까지

한 줄 요약: 메인 프로세스가 컴포넌트를 세우고, 워커를 낳고, 워커가 각자 모델을 로드합니다.

왜 이걸 배우나
"vllm serve 를 치고 나서 모델이 뜨기까지 1분 넘게 걸리는데, 그동안 뭘 하나?"

네 가지 일을 순서대로 합니다. 그리고 그중 가장 오래 걸리는 건 마지막 단계입니다 — 모델 가중치를 GPU에 올리는 것이요.

원문은 이 워크플로우를 "오늘날 프로덕션에서 가장 흔히 사용되는 구성인 멀티프로세스 설정"으로 설명합니다. tensor_parallel_size=4인 상황입니다 — 7장 7장의 그 TP입니다.

이 절이 설명하는 코드
llm = LLM(
  model="Qwen/Qwen2.5-7B-Instruct",
  # specify 4 workers
  tensor_parallel_size=4,
  # use multi-process model executor
  distributed_executor_backend="mp"
)
핵심 설정 파라미터 둘
파라미터하는 일
tensor_parallel_size워커(GPU) 개수 지정 — 이 예제에서는 4
distributed_executor_backend"mp"(멀티프로세스) = 단일 노드 다중 GPU · "ray" = 여러 머신에 걸친 멀티 노드

7장 9장에서 본 --distributed-executor-backend ray가 여기 그대로 있습니다. 단일 노드면 mp, 노드를 넘으면 ray입니다.

원문 그림 8-3

멀티프로세스 초기화 워크플로우

이 그림이 말하는 것

① 메인 프로세스가 LLMEngine · Scheduler · KVCacheManager · MultiProcessExecutor를 전부 초기화하고 설정값을 배포합니다.
② MultiProcessExecutor가 워커 프로세스 4개를 생성(spawn)하고, 명령을 내려보낼 rpc_broadcast_mq 메시지 큐를 세웁니다.
③ 각 워커가 GPUWorker를 실행합니다 — CUDA 디바이스를 설정하고, 프로세스 간 통신을 수립하고, 모델을 로드합니다. 결과 회신용으로 worker_response_mq도 유지합니다.
④ GPUModelRunner가 내부 모델 레지스트리에서 Qwen을 조회해 Qwen3NextForCausalLM 구현체를 고르고, __init__을 호출해 가중치를 GPU에 올립니다.

메시지 큐가 둘인 이유

양방향이기 때문입니다.

rpc_broadcast_mq : 메인 → 워커 (명령 하달용) worker_response_mq : 워커 → 메인 (결과 회신용)

그리고 모델 구현체 선택은 내부 레지스트리 조회 방식이라, 새 아키텍처가 나와도 레지스트리에 등록만 하면 됩니다. 이게 9장에서 볼 "미래 대비 구조"의 한 조각입니다.

그림 5

워커 수를 바꾸면 초기화가 어떻게 달라지나

↔ 슬라이더 2개 + 버튼
해볼 것 — ① tensor_parallel_size를 늘리면 어느 단계가 길어지는지 보세요. ② 모델 크기를 키우면 어느 단계가 지배하는지 봅니다. ③ 백엔드를 ray로 바꾸면 무엇이 추가되는지 확인하세요.
관찰 포인트

대부분의 시간은 4단계(가중치 로드)가 먹습니다. 워커를 늘려도 그 시간은 병렬로 나뉩니다.

5장 세 줄 요약
  1. 순서는 메인 프로세스 초기화 → 워커 생성 → 워커별 GPUWorker 실행 → 모델 로드입니다.
  2. 메인과 워커는 메시지 큐 두 개로 양방향 통신합니다 — rpc_broadcast_mq와 worker_response_mq.
  3. 모델 구현체는 내부 레지스트리 조회로 고릅니다 — 새 아키텍처를 유연하게 받기 위해서입니다.

06요청 실행 — generate() 를 부르면 벌어지는 일

한 줄 요약: 토큰화 → 스케줄 → 실행 → 출력 변환. 실제 모델이 도는 건 3번뿐입니다.

왜 이걸 배우나
"generate() 안에서 GPU가 언제 돌기 시작하지?"

4단계 중 3번에서만 돕니다. 1·2·4번은 전부 CPU 쪽 일입니다.

그리고 이 구분이 중요한 이유가 있습니다 — 스케줄러는 계획만 세우고, 워커는 실행만 합니다. 그래서 스케줄링을 개선해도 커널을 안 건드리고, 커널을 바꿔도 스케줄링이 안 깨집니다.

원문 그림 8-4

생성 요청 실행 워크플로우

이 그림이 말하는 것

① Processor가 원시 입력을 검증하고 토큰화해 Request 객체로 만듭니다.
② LLMEngine이 실행 루프를 돌며 EngineCore를 반복 호출하고, EngineCore는 Scheduler에게 "다음에 뭘 얼마나 돌릴지"를 정하게 합니다. 여기서 페이지드 어텐션, 연속 배칭 같은 최적화가 붙습니다.
③ SchedulerOutput이 MultiProcessExecutor로, 다시 GPU 워커로 갑니다. 실제 모델 forward pass가 일어나는 곳이 바로 여기입니다.
④ 모델 출력이 Output Processor를 거쳐 최종 응답이 됩니다.

단계별 담당 — 원문 표 그대로
단계담당 컴포넌트역할
1Processor입력 검증·토큰화 → Request 객체 생성
2LLMEngine → EngineCore → Scheduler다음 배치 결정, PagedAttention·Continuous Batching 등 최적화 적용
3MultiProcessExecutor → GPU Worker실제 모델 forward pass 실행
4Output Processor모델 출력 → 최종 응답 변환
그림 6

한 요청이 네 단계를 지나가는 동안

↔ 슬라이더 2개 + 버튼
해볼 것 — ① 출력 길이를 늘리면 2·3단계가 몇 번 반복되는지 보세요. ② 프롬프트를 늘리면 어느 단계가 무거워지는지 봅니다. ③ "루프 펼치기"를 켜면 decode가 왜 반복인지 드러납니다.
관찰 포인트

1·4단계는 딱 한 번입니다. 2·3단계는 출력 토큰 수만큼 반복됩니다 — 그게 자기회귀입니다.

이 절의 진짜 메시지 — 역할이 나뉘어 있습니다

원문의 정리입니다. Scheduler는 "언제, 무엇을, 어떻게 배치할지"를 결정하는 서빙 최적화(계획) 담당이고, GPUWorker는 실제 연산(모델 실행)만 담당합니다.
이 관심사 분리 덕분에 vLLM은 배칭·스케줄링 최적화를 GPU 실행 로직과 독립적으로 개선할 수 있습니다.

6장 세 줄 요약
  1. 순서는 Processor → Scheduler → GPU Worker → Output Processor입니다.
  2. GPU가 도는 건 3단계뿐이고, 2·3단계는 출력 토큰 수만큼 반복됩니다.
  3. 계획(Scheduler)과 실행(GPUWorker)이 나뉘어 있어 한쪽을 고쳐도 다른 쪽이 안 깨집니다.

07스케줄러 — 중앙 교통 관제탑

한 줄 요약: 앞 두 장에서 배운 최적화가 전부 여기 한 곳에 모입니다.

왜 이걸 배우나
"연속 배칭, 청크 프리필, 프리픽스 캐싱… 이것들이 서로 어떻게 안 부딪히지?"

한 곳에서 결정하기 때문입니다. 원문의 표현으로 스케줄러는 "모델에 무관한 성능 최적화의 중앙 통합 지점"입니다.

그리고 여기가 이 장의 심장입니다. 6장과 7장에서 배운 기법 대부분이 이 객체 안에서 일어납니다.

이 장에 나오는 낯선 말
WAITING 큐 / RUNNING 큐
아직 시작 못 한 요청 / 이미 KV 캐시 블록을 점유하고 생성 중인 요청.
토큰 예산(token budget)
이번 스텝에 처리할 수 있는 토큰 총량의 상한. 6장 5장의 max-num-batched-tokens가 이것입니다.
선점(preemption)
자원이 부족할 때 우선순위가 낮은 요청을 밀어내고 그 자리를 회수하는 것.
FCFS
선입선출(First-Come, First-Served). vLLM이 쓸 수 있는 기본 정렬 정책입니다.
스케줄러의 다섯 가지 책임 — 원문 그대로

① 요청 리소스 오케스트레이션 — 요청이 도착한 순간부터 완료까지 전체 생명주기를 조율합니다. WAITING/RUNNING 큐로 정리하고, GPU 메모리·KV 캐시 블록·토큰 예산을 보고 무엇을 실행할지 동적으로 정합니다.
② 토큰 단위 자원 할당 — vLLM은 prefill과 decode를 분리하지 않고 통합된 토큰 기반 스케줄링을 씁니다. 요청 단위가 아니라 토큰 단위로 움직입니다.
③ 최적화 통합 허브 — 프리픽스 캐싱 · 추측 디코딩 · 청크드 프리필 · 분산 KV 캐시 전송을 조율합니다. 핵심은 이걸 언제 어떻게 적용할지 적응적으로 결정한다는 것입니다.
④ 동적 부하 분산 — 도착·완료·선점·자원 한계 같은 이벤트에 대응해 매번 재평가합니다.
⑤ 요청 생명주기 관리 — FCFS나 우선순위 기반 정렬을 적용하고, 자원이 부족하면 우선순위가 낮은 요청을 선점해 용량을 재할당합니다.

08토큰 예산 — 두 숫자의 간극을 좁히는 일

한 줄 요약: 스케줄러가 하는 일은 결국 num_computed_tokens를 num_tokens_with_spec에 붙이는 것입니다.

왜 이걸 배우나
"토큰 단위 스케줄링이 요청 단위보다 낫다는 건 알겠는데, 코드로는 어떻게 생겼나?"

딱 두 숫자입니다. 그리고 그 차이를 줄이는 게 스케줄러의 전부입니다.

두 숫자
이름뜻
num_computed_tokens이미 처리된 토큰 수
num_tokens_with_spec처리해야 할 총 토큰 수 — 프롬프트 + 출력 + 추측 토큰 포함

원문의 문장 — "Scheduler는 이 둘 사이의 간극을 최소화하려 합니다. 이 간극을 좁히려는 목표가 스케줄링 중 적용되는 일련의 최적화 전략을 이끕니다."

num_tokens_with_spec에 추측 토큰이 포함된다는 게 재밌습니다 — 7장 1장의 추측적 디코딩이 이 한 변수로 스케줄러에 들어와 있습니다.

스케줄러의 핵심 루프 — 원문 그대로
while req_index < len(self.running) and token_budget > 0:
    request = self.running[req_index]
    num_new_tokens = (request.num_tokens_with_spec +
                      request.num_output_placeholders -
                      request.num_computed_tokens)

이 다섯 줄이 vLLM 스케줄러의 뼈대입니다. RUNNING 큐를 돌면서, 토큰 예산이 남아 있는 동안, 각 요청이 아직 못 한 만큼을 계산합니다. 그리고 그 값에 청크 프리필 상한이 걸리고, 프리픽스 캐시 히트가 빠지고, 남은 게 이번 스텝의 몫이 됩니다.

11SGLang — 구조화 출력과 에이전트를 겨냥

한 줄 요약: RadixAttention으로 프리픽스를 재사용하고, 구조화 출력이 오히려 빨라집니다.

왜 이걸 배우나
"vLLM 대안이 필요한 상황이 있나?"

있습니다. 에이전트 워크플로우와 엄격한 JSON 출력입니다. 둘 다 vLLM도 하지만, SGLang은 그 둘을 겨냥해 설계됐습니다.

원문의 위치 규정 — SGLang은 vLLM의 직접적인 동급 경쟁 프레임워크이고, 특히 구조화된 생성(JSON/정규식/EBNF)과 에이전트/다단계 워크플로우에 강점이 있습니다.

이 장에 나오는 낯선 말
RadixAttention
여러 호출에 걸친 KV 캐시 재사용을 트리(radix tree) 구조로 관리하는 기법. 6장 13장에서 본 그 트리입니다.
구조화된 생성
출력이 JSON·정규식·EBNF 문법을 반드시 만족하도록 강제하는 것.
점프-포워드 디코딩
문법상 이미 정해진 토큰은 모델을 부르지 않고 그냥 내보내는 것.
설계 철학과 기능

설계 철학 — 빠른 백엔드 런타임(커널, 캐싱, 스케줄링)을 유연한 프론트엔드 언어 및 API와 공동 설계(co-design)합니다. 생성을 더 빠르고 더 제어 가능하게 만드는 게 목표입니다.

핵심 기능 — RadixAttention(프리픽스/KV 재사용), 연속 배칭, 페이지드 KV, 추측 디코딩(EAGLE-2/3), 청크드 프리필, 구조화된 출력, 멀티-LoRA, 다양한 병렬화(텐서/파이프라인/전문가/데이터).

하드웨어 지원 — NVIDIA뿐 아니라 AMD Instinct, CPU, TPU, Jetson Orin, Ascend까지. TensorRT-LLM보다 훨씬 폭넓습니다.

원문 도식 재현

RadixAttention — 대화가 갈라져도 줄기는 공유합니다

이 그림이 말하는 것

에이전트가 같은 시스템 프롬프트로 여러 도구를 호출하고, 멀티턴 대화가 이어지면 줄기는 계속 같고 가지만 달라집니다. 원문의 표현 — "반복적인 프리픽스가 많은 에이전트/멀티턴 시나리오에서 강점"입니다.

뒤집히는 직관 — 구조화 출력이 오히려 빠릅니다

보통 "제약을 걸면 느려진다"고 생각합니다. 그런데 원문의 케이스북 결론은 반대입니다.

"구조화 출력이 오히려 처리량을 올릴 수 있다. 점프-포워드 디코딩이 결정된 토큰을 모델 호출 없이 방출하므로, 구조 비중이 큰 JSON 출력은 제약 없는 생성보다 빠르다. 제약을 비용으로만 생각하면 이 이득을 놓칠 수 있다."

JSON의 {"name": " 같은 부분은 문법상 이미 정해져 있습니다. 모델에게 물어볼 필요가 없습니다. 그 토큰들을 모델 호출 없이 그냥 내보내는 게 점프-포워드 디코딩입니다.

· TensorRT-LLM — NVIDIA GPU 전용, 최대 실전 성능에 특화

그리고 솔직한 현황도 적혀 있습니다 — 성능은 vLLM과 경쟁력 있는 수준이지만, vLLM이 아직 더 넓은 커뮤니티·생태계를 갖고 있다는 것이 현재 시점의 주요 차이입니다.

왜 이걸 배우나
"튜닝을 어디서부터 시작해야 하나?"

※ 원문은 이 케이스북의 "결과 의미 분석 내용 중 일부"를 인용한 것이라, 라운드별 상세 절차나 전체 수치표는 실려 있지 않습니다. 아래는 실린 결론만 옮긴 것입니다.

그림 13

어느 손잡이가 얼마나 컸나

↔ 슬라이더 + 버튼
해볼 것 — ① 항목을 하나씩 켜면서 누적 이득이 어떻게 쌓이는지 보세요. ② "모델 교체"만 켠 것과 나머지를 다 켠 것을 비교하세요. ③ 순서를 바꿔도 결론이 같은지 확인하세요.
관찰 포인트

27B → 9B 한 번이 2.75배, 이후 세 라운드 튜닝을 다 합쳐 1.6배였습니다.

① 모델 선정이 모든 설정 튜닝의 합보다 큽니다

"27B → 9B로 한번 바꿨을 뿐인데 2.75배 이득을 봤고, 이후 세 라운드의 설정 튜닝을 다 합쳐봐야 1.6배."

그래서 원문의 조언 — 튜닝 시작 전에 "이 작업을 하는 데 이 크기가 정말 필요한가"를 검증셋으로 확인하세요. 6장 12장의 증류 이야기가 여기서 실전 조언으로 돌아옵니다.

② TP는 크다고 좋지 않습니다

"TP는 개별 요청 지연을 낮추지만(메모리 자리가 많아서), 통신 비용을 늘리고 병렬 배치 기회를 줄인다. ITL SLO에 여유가 있다면 TP를 줄이고 복제를 늘리는 쪽이 처리량과 TTFT 양쪽에서 유리하다. 이 트레이드오프는 케이스마다 결론이 달라지므로 반드시 실측으로 확인해야 한다."

7장 7·9장에서 세어본 160회 대 3회가 실무에서 이렇게 나타납니다.

③ 라우팅 정책 하나로 TTFT가 2.8배 갈립니다

"복제 분할과 캐시 인지 라우팅 적용 결과: 같은 하드웨어에서 라우팅 정책 하나로 TTFT 2.8배 갈린다."
이유도 명확합니다 — "접두사 공유가 큰 워크로드에서 라운드로빈은 캐시를 무력화한다. 워커를 늘리기 전에 라우팅부터 확인해야 한다."

6장 14장과 7장 11장에서 본 그 이야기입니다. 하드웨어를 안 바꾸고 정책만 바꿔 2.8배입니다.

④ 프롬프트 구조가 인프라 설정보다 클 수 있습니다

"변하는 값을 앞에서 뒤로 옮긴 것만으로 TTFT를 절반으로 만들 수 있었다. 서빙팀과 애플리케이션 팀이 분리되어 있으면 이 문제를 아무도 발견하지 못할 것이다."

프리픽스 캐싱은 앞에서부터만 맞출 수 있습니다(6장 13장). 타임스탬프나 사용자 ID 같은 매번 바뀌는 값이 프롬프트 맨 앞에 있으면 캐시가 전부 죽습니다. 그걸 뒤로 옮기는 한 줄이 TTFT를 절반으로 만들었습니다.

⑤~⑥ 캐시는 꼬리를 고치고, 계층 캐시는 손익을 먼저 계산합니다

HiCache — "중앙값보다 꼬리값을 개선한다. 이미 캐시된 요청은 달라지지 않고 미스가 날 때 요청이 복원되기 때문에 p99 SLO가 있는 서비스에서 특히 값어치가 있다."
계층 캐시 — "도입 전에 손익 분기를 계산해야 한다. 계산 속도와 전송 비율이 1을 넘지 않으면 순손해다."

7장 13장의 "전송이 계산보다 느리면 손해"가 여기서도 같은 형태로 나옵니다. 가져오는 게 다시 만드는 것보다 느리면 캐시가 아니라 짐입니다.

⑦ 안 쓰는 기법을 빼는 것도 튜닝입니다

"투기적 디코딩 제거: 이번 케이스에서는 출력보다는 입력에 대한 최적화가 필요하므로 디코드 최적화를 위한 작업이 불필요해 투기적 디코딩을 뺀다."

7장 4장에서 배운 그대로입니다 — 추측적 디코딩은 decode 전용이고, 입력이 무거운 워크로드에서는 오버헤드일 뿐입니다.

⑧ MoE와 dense는 워크로드가 갈라놓습니다

"케이스 1(출력 400토큰 동시성 25 상황)에서는 dense가, 여기 출력(120토큰 동시성 40)에서는 MoE가 유리했다. 판단 기준은 배치가 임계 배치에 얼마나 가까운지, 출력 길이다."

7장 12장에서 본 "SPARSITY NEEDS THE BIG BATCH"가 이 판단 기준입니다. 배치가 작으면 전문가당 토큰이 몇 개 안 들어와 MoE가 GPU를 못 채웁니다.

⑨ 대형 MoE — 왜 하필 4노드 32 GPU인가

원문이 이 숫자를 고른 이유를 끝까지 설명합니다.

모델 가중치 FP8 기준 284 GB H200 한 장 141 GB → 최소 3장이면 가중치는 들어감. 그런데 KV 캐시 여유가 거의 안 남음 전문가 256개를 나눠 담으려면 GPU 수가 충분해야 함 → 32 GPU면 GPU당 8개씩 균등 배분 그럼 왜 더 크게 안 묶나? → 인스턴스가 커질수록 all-to-all 통신 범위가 넓어지고 노드 간 InfiniBand를 더 타게 됨 → 32 GPU = 노드 4대이므로 통신의 상당 부분이 노드 내부 NVLink에서 처리됨

그리고 결론 — "대형 MoE에서 병렬화 전략이 원가를 지배한다: 같은 하드웨어에서 TP만 쓴 구성과 EP + PD 분리 구성의 차이가 3배나 난다."
7장 10장과 12장이 3배라는 한 숫자로 합쳐집니다.

12장 세 줄 요약
  1. 튜닝 순서는 모델 크기 → 프롬프트 구조 → 라우팅 → 병렬화 → 캐시입니다. 위쪽이 훨씬 큽니다.
  2. 27B→9B 2.75배, 라우팅 정책 2.8배, 프롬프트 재배치 2배, EP+PD 3배 — 전부 하드웨어를 안 늘리고 얻은 것입니다.
  3. 기법을 빼는 것도 튜닝입니다. 워크로드에 안 맞는 최적화는 오버헤드일 뿐입니다.

13llama.cpp — 어디서나, 저비용

한 줄 요약: 최고 처리량을 포기하고 이식성·단순성·비용을 삽니다.

왜 이걸 배우나
"노트북에서 모델 하나 돌려보고 싶은데 vLLM은 너무 무겁다."

그 자리를 위해 만들어진 것이 llama.cpp입니다. 나머지 셋(vLLM · TensorRT-LLM · SGLang)이 데이터센터 GPU에서의 고처리량·저지연 서빙을 최우선으로 최적화한 반면, llama.cpp는 이식성, 단순성, 비용 효율성을 우선합니다.

그리고 이건 타협이 아니라 다른 목표입니다. 로컬 추론에서는 애초에 최적화하려는 것 자체가 다릅니다.

로컬 추론에서는 목표가 달라집니다 — 원문 그대로

· 플릿 전체의 초당 토큰 수가 아니라, 지연 시간과 응답성을 최적화하고 싶어집니다.
· 낮은 동시성(흔히 단일 사용자)이므로 대규모 배칭과 복잡한 스케줄러의 가치가 줄어듭니다.
· 메모리·연산·전력 측면의 풋프린트와 비용이 주요 제약이 됩니다.
· 프라이버시와 오프라인 신뢰성이 최우선 요구사항이 됩니다.

이 목록을 보면 6장·7장의 기법 대부분이 왜 여기서 의미가 줄어드는지 보입니다. 연속 배칭도, P/D 분리도, 전문가 병렬도 동시 사용자가 한 명이면 할 일이 없습니다.

llama.cpp 스택 — GGUF에서 백엔드까지

이 그림이 말하는 것

Hugging Face 체크포인트를 GGUF로 변환하고, 2~8비트로 양자화합니다. 그다음은 CPU(SIMD)가 기본이고, 있으면 Metal · CUDA · ROCm · Vulkan을 선택적으로 씁니다.
위쪽에는 llama cli와 llama serve(내장 웹 UI 포함)가 있고, 더 쉬운 REST API를 원하면 Ollama가 이 전체를 한 겹 더 감쌉니다.

6장 9·10장에서 본 양자화가 여기서는 선택이 아니라 전제입니다. CPU에서 돌리려면 모델이 작아야 하니까요.

llama.cpp로 CPU에서 Qwen3 실행
from llama_cpp import Llama

# Hugging Face에서 Qwen 모델(GGUF 포맷)을 로드
llm = Llama.from_pretrained(
   repo_id="Qwen/Qwen3-8B-GGUF",
   filename="*Q8_0.gguf",
   verbose=False
)

output = llm(
     "Q: Name the planets in the solar system? A: ",  # 프롬프트
     max_tokens=32,        # 최대 32개 토큰 생성
     stop=["Q:", "\n"],    # 모델이 새 질문을 생성하기 직전에 멈춤
     echo=True             # 출력에 프롬프트를 그대로 포함
)

13장 세 줄 요약
  1. llama.cpp는 가벼운 C/C++ 스택이고 GGUF + 2~8비트 양자화로 CPU에서도 돕니다.
  2. 로컬 추론은 최적화 목표 자체가 다릅니다 — 처리량이 아니라 응답성·풋프린트·프라이버시입니다.
  3. REST API가 필요하면 Ollama가 llama.cpp를 감싸 줍니다.

14고르기 — 벤치마크 1위가 아니라 내 SLO

한 줄 요약: 기능이 아니라 SLO부터 적고, 3~6개월마다 다시 물으세요.

왜 이걸 배우나
"결국 뭘 써야 하나?"

원문의 답은 "경우에 따라 다르다"이고, 그게 회피가 아니라 이 장의 결론입니다. 프레임워크 선택은 "벤치마크 1위"가 아니라 "내 SLO·워크로드·운영 현실에 맞는가"를 기준으로 해야 합니다.

평가 접근법 여섯 단계 — 원문 그대로

① 기능이 아니라 SLO부터 시작하라. 지연 시간(TTFT, p95/p99), 처리량(TPS/QPS), 토큰당 비용, 품질 제약(구조화된 JSON, 안전성), 가용성 목표를 적어 두기.
② 실제 프롬프트를 분석하라. prefill 위주인지 decode 위주인지, 컨텍스트 길이, 도구 호출이나 멀티턴 체인 포함 여부를 명확히.
③ 동일한 조건으로 비교하라. 같은 모델, dtype/양자화, 최대 시퀀스 길이, 배치/동시성, 스트리밍 설정으로.
④ 운영성을 측정하라. 콜드 스타트 시간, 관측 가능성, 오토스케일링 동작, 멀티테넌시 공정성, 업그레이드 마찰, 장애 모드.
⑤ 하드웨어와 벤더 종속을 고려하라. 여러 벤더를 쓴다면 이식성이 크게 중요합니다.
⑥ 변화를 계획하라. 모델 교체와 새로운 디코딩 기법은 매주 일어나므로, 큰 수술 없이 업데이트할 수 있는 프레임워크를 고르세요.

②번이 특히 중요합니다. prefill 위주인지 decode 위주인지가 7장에서 배운 거의 모든 판단(추측 디코딩을 켤지, P/D를 나눌지, MoE를 쓸지)의 입력값이었으니까요. 그리고 12장의 케이스북이 실증했듯 그걸 모르고 튜닝하면 엉뚱한 손잡이를 돌리게 됩니다.

상황별 선택 가이드

이 그림이 말하는 것

vLLM — 빠른 프로덕션 배포, 폭넓은 모델 지원, 파이썬 워크플로우. 강력한 기본 성능 + 가장 큰 생태계.

마치며 — 정착하지 말고 갈아탈 수 있게

이 장을 한 줄로 줄이면 이렇습니다.

CH8 세 줄
  1. 범용 ML 서빙 스택은 LLM에 부족합니다. 토큰 단위 스케줄링, KV 캐시 관리, 긴 컨텍스트 메모리, 스트리밍 우선 실행이 없기 때문입니다.
  2. vLLM의 중심은 스케줄러이고, 최적화는 4계층으로 나뉩니다. Scheduler → ModelExecutor → 모델 레이어 → CustomOp.
  3. 나머지 셋은 대체재가 아니라 보완재입니다. TensorRT-LLM(NVIDIA 최고 효율) · llama.cpp(경량 로컬·엣지) · SGLang(멀티 벤더 + 에이전트·구조화 출력).
이 장의 핵심 메시지 — 원문 그대로

"어떤 프레임워크가 최고인가"가 아니라 "내 상황(SLO, 하드웨어, 워크로드)에 어떤 프레임워크가 맞는가"를 물어야 합니다. 실무에서 흔한 패턴은 온라인 서빙 = vLLM + 로컬 개발 = llama.cpp 조합이지만, 요구사항에 따라 TensorRT-LLM(NVIDIA 올인)이나 SGLang(에이전트/구조화 출력)으로 전환할 수 있습니다.

가장 실천적인 결론 — 프레임워크 무관성

· 3~6개월 주기로 프레임워크 재조사
· 이식 가능한(portable) 인터페이스 선호
· 컴포넌트를 큰 수술 없이 교체할 수 있는 추상화 레이어 확보

원문의 마지막 문장입니다 — "LLM 서빙 생태계가 계속 빠르게 변하는 만큼, 특정 프레임워크에 정착하기보다는 변화에 올라탈 수 있는 유연한 서빙 아키텍처를 유지하는 것이 이 장의 최종 결론입니다."

5~8장을 한 줄로 이으면

5장 — 어디가 병목인지 재는 법(산술 강도).
6장 — 한 GPU 안에서 그 병목을 옮기는 법(배칭·KV 캐시·양자화·프리픽스 캐싱).
7장 — GPU 한 장의 경계를 넘는 법(추측 디코딩·병렬화·P/D 분리·고급 KV 캐싱).
8장 — 그 전부가 어느 코드의 어느 계층에 얹혀 있는지, 그리고 그 그릇을 어떻게 고르는지.

그래서 이 장의 12장 케이스북이 유독 잘 읽힙니다. 거기 나온 아홉 가지가 전부 앞 세 장에서 배운 것의 실전 재확인이었으니까요 — TP 트레이드오프, 라우팅과 캐시, 프리픽스 순서, 전송 대 계산, MoE 임계 배치, EP + PD.
